# API Rope Shop

Backend REST API для интернет-магазина по продаже верёвок, конфигураций изделий и услуг сращивания (splicing).

## Стек технологий
- **Язык**: Python 3.12+
- **Фреймворк**: FastAPI, Pydantic v2
- **База данных**: PostgreSQL, SQLAlchemy 2.0 (asyncpg)
- **Миграции**: Alembic
- **Тестирование**: Pytest, pytest-asyncio
- **Контейнеризация**: Docker, Docker Compose

---

## Быстрый запуск

### 🚀 Вариант 1 (Рекомендуемый) — Единый скрипт автоматизации `src/tools/run.py`

Для быстрого развёртывания, управления контейнерами и инициализации данных подготовлен скрипт `src/tools/run.py`.

#### Возможности скрипта:
- **Проверка Docker**: автоматически валидирует наличие установленного Docker и активность демона Docker Desktop.
- **Автоматическая настройка `.env`**: если файл конфигурации `.env` отсутствует, скрипт генерирует его из `.example.env`, подставляет стойкие случайные ключи (`SECRET_KEY`, `DB_PASSWORD`, `ADMIN_PASSWORD`) и сохраняет данные суперпользователя в файл `ADMIN_CREDENTIALS.txt`.
- **Сборка и запуск контейнеров**: выполняет сборку образов и фоновый запуск контейнеров с флагом ожидания готовности (`--wait`).
- **Синхронизация Nginx**: при использовании стека с Nginx автоматически перезапускает его для корректного резолва DNS и апстримов.
- **Интеллектуальный Health Check**: пингует ключевые эндпоинты API и сообщает об их статусе (HTTP 200 OK).
- **Управление БД**: предоставляет быстрые команды для запуска миграций Alembic и генерации тестовых данных.

#### Основные команды:
```bash
# 1. Запуск проекта (по умолчанию выполняется start)
python src/tools/run.py
# или явно:
python src/tools/run.py start

# 2. Остановка проекта и контейнеров
python src/tools/run.py stop

# 3. Проверка доступности запущенных сервисов (healthcheck)
python src/tools/run.py check

# 4. Применение миграций базы данных (Alembic upgrade head)
python src/tools/run.py migrate

# 5. Заполнение базы данных тестовыми данными
python src/tools/run.py seed

# 6. Вывод справки по командам и параметрам
python src/tools/run.py help
```

#### Флаги конфигурации стека:
- **По умолчанию** (`docker-compose.yaml`): запускает полный стек разработчика (Nginx + Frontend + FastAPI с автоперезагрузкой `--reload` + PostgreSQL + Redis):
  - Главная страница магазина (HTML): [http://localhost](http://localhost)
  - Каталог товаров: [http://localhost/catalog/](http://localhost/catalog/)
  - Панель администратора: [http://localhost/admin/](http://localhost/admin/)
  - Документация API: [http://localhost/docs](http://localhost/docs) или [http://localhost:8018/docs](http://localhost:8018/docs)
- **`--prod`**: запускает полный production-стек (`docker-compose.prod.yaml`) с Uvicorn workers и Nginx на порту `80`:
  ```bash
  python src/tools/run.py start --prod
  ```
- **`--local`**: запускает стек на альтернативном порту `8080` (`docker-compose.local.yaml`), если 80 порт занят:
  ```bash
  python src/tools/run.py start --local
  ```

#### Публикация в интернет через туннель (Tuna / Ngrok):
Так как сайт и API объединены через Nginx на порту `80`, для публикации всего магазина и админки наружу достаточно одной команды:
```bash
tuna http 80
```
*(Все страницы, статика, конфигуратор канатов, вход в админку и запросы к API будут мгновенно работать по единой ссылке).*

### 🛠️ Вариант 2 — Ручной запуск через Docker Compose

#### 1. Подготовка переменных окружения
Скопируйте шаблон переменных окружения:
```bash
cp .example.env .env
```
> **Важно:** при запуске в Docker убедитесь, что в `.env` указано `DB_HOST=postgres`. При локальном запуске вне контейнера используйте `DB_HOST=localhost`.

#### 2. Запуск контейнеров
Соберите и запустите сервисы:
```bash
docker compose up -d --build
```
Сервис API запустится на порту `8018`.

#### 3. Инициализация базы данных
Для создания структуры БД выберите один из вариантов:

- **Вариант 1 (рекомендуемый) — применение миграций Alembic:**
  ```bash
  docker compose exec backend_rope_shopo alembic upgrade head
  ```
  *(или локально: `alembic upgrade head`)*

- **Вариант 2 — запуск скрипта создания БД и таблиц:**
  ```bash
  docker compose exec backend_rope_shopo python -m src.tools.creating_db
  ```
  *(или локально: `python -m src.tools.creating_db`)*

#### 4. Заполнение базы данных тестовыми данными (опционально)
Для наполнения БД демонстрационными/тестовыми данными выполните:
```bash
docker compose exec backend_rope_shopo python -m src.tools.create_test_data
```
*(или локально: `python -m src.tools.create_test_data`)*

## Бизнес-процессы и архитектурные правила проекта

### 1. Каталог товаров и мультиязычность (Catalog & Localization)

* **Иерархия каталога**:
  * **Категории (`categories`)**: древовидная структура разделов со `slug`, иконками и порядковыми индексами.
  * **Товары (`products`)**: типы изделий (`rope`, `hardware`), базовые единицы измерения (`price_unit`), флаг наличия конфигуратора (`has_configurator`) и тип конструкции (`construction_type`).
  * **Варианты (`variants`)**: размерные параметры конкретного товара (диаметр в мм, вес, разрывная нагрузка, цена за метр).
  * **Цвета (`colors`)**: палитра цветов со связью с конкретными товарами (`ProductColor`).
  * **Спецификации (`specifications`)**: табличные технические характеристики (название/значение).
  * **Сферы применения (`applications`)**: целевое назначение каната (фал, шкот, лебедка, швартов и т.д.).

* **Мультиязычность и локализация (ISO 639-1 / ISO 639-2)**:
  * Все пользовательские сущности имеют дочерние таблицы переводов (`ProductTranslation`, `CategoryTranslation`, `SpliceTypeTranslation` и т.д.).
  * Поддерживаются международные двухбуквенные коды стандарта **ISO 639-1** (`ru`, `en`, `de`), а также сохранена полная обратная совместимость с трёхбуквенными кодами **ISO 639-2** (`rus`, `eng`, `ger`).
  * При передаче параметра `locale` API возвращает локализованные поля (`name`, `description` и т.д.) с автоматическим fallback на основной язык при отсутствии конкретного перевода.
  * **Правило удаления переводов**: запрещено удалять единственный оставшийся перевод сущности (`TranslationDeleteError` -> `400 Bad Request`).

* **Пагинация и контракты ответов API**:
  * Списочные эндпоинты (`GET /products`, `GET /categories`, `GET /quote_requests`) возвращают унифицированные объекты с метаданными пагинации: `items`, `total`, `skip`, `limit`.
  * Детальные эндпоинты (`GET /products/{id}`, `GET /products/by-slug/{slug}`) возвращают строгую схему `ProductDetailResponseDTO`, исключающую недетерминированный `Union`/`anyOf` в схеме OpenAPI.

### 2. Конфигураторы изделий (Configurators Domain)

Конфигуратор позволяет клиентам проектировать индивидуальные канаты с законцовками или заказывать услуги сплайсинга:

* **3 бизнес-сценария работы (`ConfiguratorType`)**:
  1. **`ROPE_WITH_SPLICE` (Канат с заделкой / Готовое изделие)**:
     * Клиент выбирает канат из каталога, диаметр, цвет, длину отреза и тип законцовки на обоих концах (Конец A и Конец B).
     * Доступны сопутствующие дополнительные опции (маркировка, сертификаты, чехлы, пропитка).
  2. **`LOOP_ONLY` (Только петли / Давальческий канат)**:
     * Услуга изготовления петель на собственном канате заказчика.
     * Выбор тарифной группы материала заделки (`SpliceMaterial`), типа петли, диаметра каната и применимых доп. опций (опции с пометовой тарификацией исключаются).
  3. **`SPLICE_ONLY` (Сращивание / Ремонт каната)**:
     * Услуга сращивания двух концов каната (соединительный сплайс, бесконечная петля).

* **Архитектурное разделение эндпоинтов**:
  * **`GET /configurators` (Клиентский бандл инициализации)**:
    * Отдаёт полный сводный пакет данных (глобальные настройки, тарифные группы, типы заделок, матрицу цен, доступные товары с вариантами и цветами) за **один HTTP-запрос**.
    * Позволяет фронтенду закэшировать состояние и работать мгновенно без сотен повторных запросов к серверу при переключении шагов.
  * **`GET /configurators/price` (Серверный расчёт цены заделки)**:
    * Принимает `material_id`, `splice_type_id`, `diameter_mm` и возвращает точную стоимость операции по правилам матрицы цен для фронтенда, не желающего вычислять матрицу на клиенте.
  * **`/rope_products` и `/rope_variants` (Административное управление)**:
    * Служебные и административные CRUD-эндпоинты для управления конфигурационными параметрами каната (`RopeConfiguratorSetting`, разрешённые типы заделок, варианты диаметров).

### 3. Математика расчёта стоимости заявки (Pricing Engine)

Расчёт стоимости в модуле `quote_requests` строго регламентирован:

* **Технологический припуск длины на сращивание (`Splice Allowance`)**:
  * Заделка конца каната требует расхода материала на вплетение сердечника/оплётки.
  * Если на конце A или конце B выбрана заделка, к полезной длине каната $L$ автоматически прибавляется припуск:
    * При диаметре $\le \text{splice\_allowance\_until\_mm}$: прибавка $\text{splice\_allowance\_until\_m}$ на каждый сплайс.
    * При диаметре $> \text{splice\_allowance\_until\_mm}$: прибавка $\text{splice\_allowance\_over\_m}$ на каждый сплайс.
  * Эффективная длина: $L_{\text{eff}} = L + \Delta L_{\text{allowance}}$.

* **Формула расчёта позиции каната (`QuoteRopeItem`)**:
  * $\text{total\_rope\_cost} = \text{round}(\text{price\_per\_meter} \times L_{\text{eff}} \times \text{quantity}, 2)$
  * $\text{end\_a\_cost} = \text{round}(\text{unit\_price}_{\text{end\_a}} \times \text{quantity}, 2)$
  * $\text{end\_b\_cost} = \text{round}(\text{unit\_price}_{\text{end\_b}} \times \text{quantity}, 2)$
  * Итого по позиции: $\text{total\_cost} = \text{total\_rope\_cost} + \text{end\_a\_cost} + \text{end\_b\_cost}$.

* **Схемы тарификации дополнительных опций (`QuoteExtraItem`)**:
  * **`FIXED`**: фиксированная стоимость за опцию в заказе.
  * **`PER_ITEM`**: тариф умножается на общее количество изделий/операций в заявке.
  * **`PER_METER`**: тариф умножается на суммарный чистый метраж каната во всех позициях.

* **Надбавка за срочность (`is_urgent`)**:
  * Суммируется общее количество операций сращивания во всей заявке ($\text{total\_splices}$).
  * Если $\text{total\_splices} > \text{urgent\_max\_splices}$ — валидация отклоняет заявку (`QuoteRequestValidationError`).
  * При $\text{is\_urgent} = \text{true}$: $\text{urgent\_surcharge} = \text{round}(\text{total\_splices} \times \text{urgent\_surcharge\_per\_splice}, 2)$.
  * Итоговая сумма заявки: $\text{total\_price} = \sum \text{items} + \sum \text{services} + \sum \text{extras} + \text{urgent\_surcharge}$.

### 4. Паттерн слепка заказа (Order Snapshot Pattern)

Заявка клиента фиксирует финансовые и технические параметры на момент заказа:
* **Неизменяемость цен**: при создании `QuoteRequest` сохраняются зафиксированные цены (`price_per_meter`, `unit_price`, `total_cost`), названия товаров и характеристики. Дальнейшее изменение цен в прайс-листе не влияет на оформленный заказ.
* **Целостность данных при удалении товаров**:
  * Внешний ключ `QuoteRopeItem.product_id` настроен со стратегией `ON DELETE SET NULL`.
  * При удалении товара из каталога исторические заявки не разрушаются: сохраняются все параметры, применённые материалы, длина и расчёты.

### 5. Жизненный цикл данных и правила удаления

В соответствии с `rules_project.md §5.1`:
* **Запрет каскадного разрушения**: если сущность используется в активных связях (например, категория с товарами, цвет с привязками к канатам, тип заделки с ценовыми правилами), удаление блокируется методом `has_dependencies()` репозитория с выбросом кастомного исключения `<Entity>HasDependencies` (`400 Bad Request`).
* **Каскадное очищение зависимостей**:
  * При разрешённом удалении товара каскадно удаляются зависимые спецификации, привязки цветов, конфигурационные настройки и изображения.
  * Все связанные медиафайлы физически удаляются с диска сервера через сервис `handlers_files` и `PathBuilder`.

### 6. Архитектура слоёв и обработка исключений

Проект строго придерживается принципа разделения ответственности:
1. **Views (`views.py`)**: принимают HTTP-запросы, валидируют входные параметры Pydantic-схемами, вызывают методы сервисов и возвращают типизированные DTO.
2. **Services (`service.py`)**: инкапсулируют бизнес-логику, управляют транзакциями (`commit`/`rollback`). **Сервисы никогда не выбрасывают `HTTPException`** — только специализированные доменные исключения (`ServiceException`).
3. **Repositories (`repository.py`)**: отвечают исключительно за исполнение SQL-запросов к PostgreSQL через SQLAlchemy 2.0 без транзакционных коммитов.
4. **Exception Handlers (`exception_handler.py`)**: централизованный слой маппинга доменных исключений в статусы HTTP:
   * `ValidationError` / `<Domain>ValidationError` -> `400 Bad Request`
   * `NotFoundData` -> `404 Not Found`
   * `PermissionErrorService` -> `403 Forbidden`
   * `DataAlreadyExists` / `IntegrityError` -> `409 Conflict`
   * `ServiceException` -> `500 Internal Server Error`
